# PLAN_FREE_TIER: the browser form, Google Drive and browser models

Status: an idea. No phase is on the board; the operator moves it to the root when it becomes a plan.

A free form of the tool that runs in the user's browser: the user's Google Drive holds the documents
and the index files, browser models compute the embeddings and the chat, and an example corpus of
invented witness statements arrives over HTTP. The AWS form (`PLAN_CONCORDANCE.md`) stays the paid
form, with the contradiction engine, gated by Google sign-in and an email allowlist.

The browser form is a third form behind the seams the laptop form already uses: models through
`packages/core/providers/modelProvider.mjs`, the store through the `{ query, close }` shape of
`packages/core/db.mjs`, text extraction through PDF.js. The eval (`evals/run.mjs` over
`evals/<corpus>/gold.jsonl`) is the proof of each phase, the way `PLAN_LAPTOP_STACK.md` uses it.

### Browser embeddings model

Runtime: Transformers.js (`@huggingface/transformers` 4.3.1) over ONNX Runtime Web
(`onnxruntime-web` 1.30.0). `device: "webgpu"` selects WebGPU; the WASM backend is the fallback;
`dtype` selects `fp32`, `fp16`, `q8` or `q4` ([WebGPU guide](https://huggingface.co/docs/transformers.js/en/guides/webgpu)).
The guide puts global WebGPU support at about 85% (caniuse, March 2026). Model files are fetched from
the Hub and cached in the Cache API (`env.useBrowserCache`, default true;
[env reference](https://huggingface.co/docs/transformers.js/en/api/env)). The embeddings run in a
Web Worker so that the page stays responsive.

does, so a model change is a re-embed, never a silent mismatch.

The originals are never altered (product rule). The index is a derived record that carries the
SHA-256 of the original bytes, computed in the browser with `crypto.subtle.digest`.

### Google auth

The direct answer to the operator's question: yes. [Sign in with Google](https://developers.google.com/identity/gsi/web/guides/overview)
(Google Identity Services) runs in the browser and returns an ID token, a JWT signed by Google.
The backend verifies that JWT with Google's public keys and never calls Google per request; the
`tokeninfo` endpoint is the call-home form and Google marks it for debugging
([verification guide](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token),
[OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)). The checks:
the signature against the JWKS at `https://www.googleapis.com/oauth2/v3/certs` (honour its
`Cache-Control`); `aud` equals the web client id; `iss` is `accounts.google.com` or
`https://accounts.google.com`; `exp` in the future; `email_verified` true; then the `email` claim
against the allowlist. `sub` is the stable user id; `email` is the allowlist key because the
operator writes emails.

Drive access is a separate token: the GIS token client (`initTokenClient`,
[token model](https://developers.google.com/identity/oauth2/web/guides/use-token-model)) is the
implicit grant in the browser, returns a short-lived access token with no refresh token, and the
page calls `requestAccessToken()` again from a click when it expires. That token stays in the
browser and never reaches AWS.

Design that follows: the page signs in with GIS (scopes `openid email`); the HTTP API routes
(`/doc`, `/facts`, `/reports`, `/spend`) carry the ID token as `Authorization: Bearer` through the
JWT authorizer; the WebSocket `$connect` carries it to the Lambda REQUEST authorizer; both check
`email_verified` and the allowlist from `/concordance/allowed-emails`; the Cognito user pool and
`packages/ui/auth.js`'s `USER_PASSWORD_AUTH` leave. The ID token lives about an hour (unchecked);
GIS re-issues it with One Tap or a click, and the page reconnects the WebSocket with the new token.

OAuth consent screen: `drive.file`, `drive.appdata`, `openid`, `email` and `profile` are
non-sensitive ([Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth));
`drive.readonly`, `drive` and `drive.metadata.readonly` are restricted and need restricted-scope
verification and an annual security assessment. The plan needs `drive.file` and `openid email`
only. [Brand verification](https://support.google.com/cloud/answer/13464321) applies to every app:
a homepage on a verified domain that describes the app, a privacy policy on the same domain linked
from both, domain ownership in Search Console. `concordance.polycode.co.uk` (row A6) is the domain.
Until verification, the consent screen in Testing mode serves the listed test users (the cap and
the token lifetime in Testing mode are unchecked).
